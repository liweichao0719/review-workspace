# 通用审查工作区：讨论与决策总结

更新日期：2026-07-31

## 1. 项目背景

目前存在四种人工审查场景：

| 所属项目 | 审查任务 | 当前实现 | 核心对象 |
|---|---|---|---|
| FIDIC RAG | 条款审计 | Streamlit | 问题、标准条款、检索证据 |
| FIDIC SFT | 数据标注 | Streamlit | 问题、答案、条款引用 |
| RiskPath | 文章筛选 | aiohttp + 原生 HTML/CSS/JS | 文章、来源、收录决定 |
| RiskPath | 节点与关系审核 | 生成式静态 HTML | 原文、风险节点、脆弱性、因果箭头 |

四种场景的业务对象不同，但人工流程高度相似：

```text
加载数据 → 列表与筛选 → 查看原文和模型结果
→ 人工判断或修改 → 保存 → 查看进度
```

现有页面分别开发，导致布局、保存方式、快捷键和进度统计重复实现。FIDIC 的
Streamlit 页面适合快速验证，但复杂内容的可读性和交互控制不足；RiskPath 的 Web
页面更清晰，但与文章流水线强耦合；静态 HTML 适合展示，却不适合可靠编辑与保存。

## 2. 项目目标

建立一个独立的、多项目人工审查工作区，统一稳定的审查基础设施，同时保留每个项目
独立的数据格式、详情布局、审核动作和校验规则。

项目首先服务本地单人审查，但结构应允许后续增加：

- 新项目和新任务；
- 数据版本与审查历史；
- 批量操作和导入导出；
- 多人协作与权限控制。

## 3. 核心原则

### 3.1 通用的是流程，不是业务字段

公共层负责项目切换、任务选择、列表、筛选、进度、保存状态、快捷键和审计记录。
“正确条款”“是否收录”“风险关系是否成立”等判断仍由项目插件定义。

### 3.2 数据格式通过适配器隔离

```text
项目原始数据 → Python 适配器 → 统一 API 模型 → 项目任务界面
```

JSONL、CSV、数据库结构或字段名发生变化时，只修改对应适配器。平台核心不得写死
RAG、SFT 或 RiskPath 的目录和字段。

### 3.3 审核结果与原数据分离

审核记录单独保存，并至少包含：

- 稳定的项目、任务和样本 ID；
- 原始数据集版本或内容指纹；
- 审核值、状态、备注和时间；
- 审核结构版本。

这可以避免重新生成数据或升级字段后丢失人工结论。

### 3.4 显式选择项目和任务

不依赖自动猜测数据类型。用户先选择项目，再选择审查任务，平台据此加载对应适配器、
详情组件、审核动作、校验和导出规则。

## 4. 技术决策

采用独立项目，而不是继续放在 RAG 或 RiskPath 内部。

- 后端：FastAPI + Pydantic；
- 前端：React + TypeScript + Vite；
- 审核存储：SQLite；
- 原始数据：继续允许 JSONL、CSV、JSON 和现有数据库；
- 项目接入：Python 适配器；
- 任务差异：React 任务组件。

没有直接选择现有四套技术实现：

- Streamlit 保留为旧工具，但不作为长期平台基础；
- 静态 HTML 的视觉表达可以复用，存储方式不复用；
- RiskPath Web 工作区的双栏布局、筛选和快捷键值得借鉴；
- `aiohttp + 原生 JS` 在单一任务中可靠，但多个差异较大的任务会增加维护成本。

## 5. 建议架构

```text
React 工作区
├── 公共外壳：项目/任务切换、列表、筛选、进度
├── RAG 条款审计组件
├── SFT 数据标注组件
├── RiskPath 文章审核组件
└── RiskPath 节点关系组件
             │
          FastAPI
├── 统一查询与保存 API
├── 适配器注册表
├── 审核记录与数据版本
└── 项目适配器
    ├── fidic_rag
    ├── fidic_sft
    ├── riskpath_article
    └── riskpath_graph
```

统一 API 只提供最小公共契约。项目专属内容可以保存在结构化扩展字段中，并由对应任务
组件解释，避免为了“统一”不断扩大公共模型。

## 6. 实施顺序

1. 保留四个旧页面，不阻断当前工作。
2. 建立公共外壳、适配器协议和独立审核存储。
3. 用约 20 道 FIDIC RAG 样本完成第一个可编辑闭环。
4. 接入 SFT，验证同一项目下不同任务的边界。
5. 接入 RiskPath 文章审核，验证跨项目能力。
6. 最后接入节点与关系审核，验证复杂结构化编辑。
7. 四种任务稳定后，再决定是否引入正式插件清单、用户系统和部署能力。

## 7. 泛化的验收标准

平台是否真正通用，不以公共代码数量衡量，而以以下结果衡量：

- 新增任务时无需修改平台核心；
- 原数据字段变化时只修改适配器；
- 项目可以拥有完全不同的详情视图和审核动作；
- 审核结果在数据升级后仍能追踪和迁移；
- 四种现有任务都能通过相同的导航、保存和进度基础设施运行。

## 8. 当前不做

- 不立即删除或替换旧页面；
- 不直接修改 RAG 和 RiskPath 的原始数据；
- 不在第一版建设复杂插件市场；
- 不在业务尚未稳定前抽象所有字段；
- 不把训练、检索或采集流水线运行逻辑塞入审查平台。

## 9. 下一步

截至 2026-07-31，FIDIC RAG 的 20 题小规模审计闭环已完成：

```text
读取样本 → 列表筛选 → 问题与条款对照 → 保存审核
→ 重启后恢复 → 导出审核结果
```

当前页面明确分开展示两类结果：两次独立语义审计结论，以及通过现有检索器重新生成的
中文 Dense、英文 Dense、中文 BM25 和 RRF Top 10。检索结果保存为带问题哈希与配置的
独立快照，并纳入数据版本指纹，不与 LLM 审计结论混淆。

下一步是用真实人工审查反馈确定公共组件边界，修正字段和交互后，再接入 SFT。

## 10. 本轮讨论结论与执行状态

本轮进一步确认：四个旧页面在技术实现上分别使用 Streamlit、aiohttp 原生 Web 和
生成式静态 HTML，但业务骨架相似，都是“加载—筛选—对照—判断/修改—保存—统计”。
因此不应从四种旧实现中直接选择一个继续膨胀，而应建立独立平台。

关于通用性，最终采用以下边界：

- 公共平台统一项目/任务选择、列表、筛选、进度、保存、版本和导出；
- Python 适配器吸收 JSONL、CSV、数据库和字段变化；
- React 任务组件保留不同项目的详情布局、审核动作和校验规则；
- 审核结果使用稳定样本 ID 和数据内容指纹关联，不直接改写项目原数据；
- 项目与审查任务显式选择，不根据输入文件自动猜测。

独立项目已建立，并完成第一个 FIDIC RAG 真实闭环。20题人工裁决本身尚未完成；
当前正确状态是“平台功能完成、人工试用进行中”。旧的四个页面继续保留，待对应任务
迁移并验证一致后再决定是否停止维护。

## 11. FIDIC 最终开发集接入（2026-08-03）

平台不再以20题试审或95题混合数据作为 FIDIC 审查来源，而是只读取冻结的
`human_gold_dev192_v1`。这不是把模型候选继续展示给人工，而是提供一个可复核、
可提出独立修订的最终数据入口。

- 审查对象固定为题型、问题、标准答案和完整上下文条款；
- 检索排名与召回评测保留在 RAG 实验流程，避免与数据质量审查混淆；
- 任何修改只进入 SQLite 的版本化审查记录，冻结源数据不被页面回写；
- 后端校验答案中的精确条款引用与选定上下文必须一一对应，防止再次出现“答案引用存在、上下文未展示”的问题。

这次接入完成的是 FIDIC 任务的生产可用闭环；SFT 与 RiskPath 的不同字段和编辑逻辑仍应通过各自适配器逐项接入，不应复制 FIDIC 页面。

## 12. 当前方向调整与多类型契约（2026-08-17）

旧 SFT 数据及旧 RiskPath 页面不再作为下一阶段的直接迁移目标。当前主线调整为先验证
平台能否稳定承载差异明显的数据类型，再根据仍在使用的真实数据源实施接入。

- 前端拆分为公共 `WorkspaceShell`、任务注册表和专属任务组件；
- 任务通过 `renderer_key` 选择组件，公共层不再读取 FIDIC 字段；
- 数据版本按任务生成，条目专属校验和审核恢复由适配器负责；
- 新增默认关闭的10条合成文章筛选任务，验证文章字段、收录决定、标签、证据摘录和
  专属校验无需进入公共 API 或 `ReviewStore`；
- 下一种代表性类型为节点—关系编辑，之后再整理当前有效的真实数据源。

新的验收重点是：新增数据类型时，只增加适配器、任务组件及注册项，不修改公共工作区、
统一 API 和审核存储的业务语义。
